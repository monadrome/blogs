# Agent 跑偏应对方案分析：从人工纠偏四级体系到自动蝴蝶效应

> Agent 最棘手的失败，往往是代码能编译、测试也通过，却解决了另一个问题：修复超时变成重写网络层，兼容旧接口变成修改调用方。本文综合两份独立产出的调研——一份覆盖 Anthropic 官方文档与中文社区实践的纠偏方法调研（8 个来源），加 omha 项目"自动蝴蝶效应"的实现剖析；一份从零开始的独立网络调研（OpenAI Codex、Cursor、Chroma、AWS 等 9 个来源）——回答一个问题：**跑偏如何尽早被发现、多低成本被纠正，以及人工纠偏的哪些环节可以自动化。**

## 一、先归因：Agent 为什么跑偏

纠偏手段取决于跑偏原因。社区共识把根源归为三类：

| 根源 | 机制 |
|------|------|
| **假设叠加** | LLM 的统计偏置是"强行给解"而不是追问缺失信息。每个假设都是一次抛硬币，串起来就是"能跑但不对"的代码 |
| **解空间太开放 × 隐式上下文不足** | 解法越开放、依赖的隐式知识越多，选错路概率越高。且 Agent **不会在工作中学习**——每次新会话都是"新员工"，不知道团队约定 |
| **长对话漂移** | 上下文污染、目标漂移、摘要失真、指令层级混杂、**错误自增强**（错误假设滚雪球）、记忆策略不稳、工具结果原始注入，七大机制叠加 |

换一个视角，独立调研把同样的问题表述为**三个反馈缺口**：

1. **需求没有变成可判断的边界。**"优化登录体验"没有说明哪些行为必须保持，也没有定义完成条件，Agent 就只能自行补全。OpenAI 的 Codex 最佳实践要求同时给出目标、上下文、约束和完成标准；工程上应把"补全得是否合理"转化为"结果是否符合契约"。
2. **信息仍在上下文里，不等于能被可靠使用。**《Lost in the Middle》发现相关信息的位置会影响模型表现，长输入中部尤其容易被忽略；Chroma 评估 18 个模型后发现，约 300 token 的相关片段比约 113k token 的完整历史表现更好。这些结果支持控制噪声，但不能直接换算成编码跑偏率，也推不出通用的上下文占用阈值。
3. **失败尝试会成为下一轮的工作前提。**错误方案一旦落进文件，后续修改就围绕它修补——即使目标被重新强调，代码状态仍在推动错误方向。这就是"错误自增强"。

还有一个常见混淆需要澄清：**context rot ≠ context drift**。context rot 是长输入下的能力衰减，context drift 是工作逐渐偏离目标——前者只是后者的一种诱因，不应把所有跑偏都归结为"模型忘了"。

一句话：**纠偏的本质是打断"错误自增强"回路，把上下文重置到干净锚点。** 所有有效手段都是这句话的具体化。

## 二、人工纠偏体系：按成本分层的四级 + 预防

### Level 1：跑偏进行中——秒级打断

- **Esc 中断**：发现方向不对立刻按 Esc，上下文保留，直接给新指令转向。Anthropic 官方原则是 **"Course-correct early and often"**——纠偏越快，结果越好、越快
- **中途插话**：Agent 工作时排队补充约束（如"别动 X 文件"）
- **重锚定提示词**：

```text
请暂停。当前目标是 X，约束是 Y 和 Z，已确认不做 W。复述你的理解再继续。
```

两个注意事项：其一，实测表明这类话术**有时不生效**——失效本身就是该升级手段的信号；复述正确只能证明生成了正确文本，必须通过后续动作检查判断是否真正恢复。其二，**有效纠偏要包含证据**，而不是空泛的方向纠正。例如："契约要求保留同步接口，但 diff 将其改成了 async；恢复签名，只修改重试条件，并运行边界测试。"——这样的反馈能直接缩小下一步的搜索空间。

### Level 2：刚跑偏完——分钟级回滚

- **`Esc + Esc` / `/rewind`**：Claude Code 检查点可分别恢复"仅对话 / 仅代码 / 两者"。局限：Bash 命令造成的文件改动、后台 subagent 的编辑**不在快照内**，检查点不能替代 git
- **"Undo that"**：让 Agent 自己撤销刚才的改动
- **git 兜底**：`git checkout .`，或开 task 前先 commit；多 Agent 并发用 git worktree 物理隔离
- **`/branch` 分叉**：保留当前会话，开分支试另一种方案

**恢复时必须同时核对会话、文件和外部状态。**只清空对话，错误代码依然存在；只恢复代码，旧对话仍可能诱导重做。数据库写入、消息发送、部署等外部副作用通常不在任何恢复范围内，需要单独补偿。回退前先辨认用户改动，避免整棵工作区无差别还原。

### Level 3：反复纠不正——重启（关键法则）

**"两次纠正法则"**：同一问题在同一会话纠正超过 2 次仍失败，清空会话开新的，把学到的东西写进更精确的初始 prompt。Cursor 同样建议在反复犯错时从修订后的计划重来。**干净会话 + 好 prompt 几乎总是胜过堆积纠正的长会话。**

但要把这条法则当**经验信号，而不是硬性次数限制**：同一失败也可能源于环境故障、缺失权限或不可满足的需求，清空上下文不会修复这些原因；反过来，一次高风险越界就应该立即停机。升级应依据失败类型、重复证据和损害预算，而不是单纯的次数。

上下文断裂的识别信号：Agent 突然换技术栈、忘记已定的方案、代码风格突变、重复问已答过的问题。

**重启前先保存交接状态**：已确认事实、失败原因、当前 diff、未解决问题及测试结果；新会话应重新读取代码、核对交接记录，而不是只凭摘要继续。

### Level 4：验收层——不接受"口头修复"

最容易被忽视的一层。**"看起来修好了"是纠偏最大的假阳性**：

- **证据五问**：①检查了哪些文件？②定位到什么？③打了什么 patch？④build 过了吗？⑤**什么检查能证明原问题真的消失了？** diff 合理 ≠ 修复，build 通过 ≠ 行为正确
- **测试门禁**：测试不过 = 任务没完，把失败输出回喂给 Agent 自修复。有实测称此举把"Agent 改坏东西"的比例降了约 80%——注意该数字缺少样本和指标定义，只能当方向性参考，不能外推
- **要证据不要断言**：测试输出、运行截图、命令返回值——审查证据比自己重跑验证快得多；且证据需要绑定提交与可信执行记录
- **Fresh-context 评审**：用新 subagent 只看任务契约、diff 和验收标准，逐条报告"违反了哪条、位置在哪、影响是什么"，不受产生代码的推理过程影响。注意"找问题"的提示可能催生无关改进，评审范围要收窄

### Level 0：预防——最便宜的纠偏是不跑偏

1. **先规划后写码**：plan mode 在写码前显式暴露假设；复杂改动先审查方案和预计影响文件
2. **开工前固定验收契约五项**：目标行为、允许改动范围、必须保持的接口、明确不做的事项、验收命令。例如："修复重试次数多一次的问题；保持函数签名和退避策略；不引入依赖；新增边界用例并通过现有回归。"
3. **收紧解空间**：prompt 更 directive；大任务拆小，人留在决策环里
4. **约束持久化**：长期规则放进 CLAUDE.md / AGENTS.md / Cursor Rules，当前任务事实单独保存。约定不落盘等于不存在；但注意注意力预算，三家官方建议都强调简洁、具体，不要把所有知识塞进常驻规则
5. **上下文卫生与长任务状态管理**：一个对话一个任务；任务间 `/clear`；长任务主动压缩。长任务按"复现、实现、验证"形成可验收的工作单元；交接摘要至少保留**目标、禁止事项、已确认决策、修改文件、验证结果和下一步**，并把事实与推测分开——推翻了此前方案就要明确标记其失效。上下文管理的目标是保住决策依据，单纯缩短文本并不够

### 速查表：症状 → 手段

| 症状 | 首选手段 | 升级路径 |
|------|---------|---------|
| 单处误解，整体方案仍成立 | Esc 中断 + 含证据的纠正 | 重锚定提示词 |
| 开始无关重构、扩大依赖或修改范围 | 停止写入，审查 diff，撤销越界部分 | git checkout |
| 改完发现不对 | "Undo that" / `/rewind` | git checkout |
| 想对比两种方案 | `/branch` 或 rewind 后换 prompt | worktree 并行 |
| 纠了 2 次还错 | **重开会话**（带保存的交接状态和新 prompt） | 拆小任务再试 |
| 说修好了但存疑 | 要证据（测试输出/截图） | fresh subagent 评审 |
| 同类错误跨会话反复出现 | 写入 CLAUDE.md / rules | 加 lint/test 门禁 |
| 长任务越跑越偏 | 周期性重锚定 + 交接摘要 | 改为"复现-实现-验证"工作单元 |

**核心心法**：纠偏要快（early and often）、要狠（反复不成就重开，不恋战）、要闭环（没证据不算修完）、要前移（预防比纠正便宜一个数量级）。

## 三、人工体系的缺口：每个环节都假设"有人在盯着"

四级体系很完整，但它有一个隐含前提：**人始终在场，且注意力在线。**而夜间批处理、一人并行监督多个任务、长时间工具调用，都是这个前提不成立的真实场景。

把纠偏流程拆开看，每一步的成本都在人身上：

| 环节 | 人工做法 | 自动化难点 |
|------|---------|-----------|
| ① 发现跑偏 | 人盯着输出，觉得"不对劲" | **变了 ≠ 漂了**：文件哈希变化只是变化的证据，不是因果漂移的证明。测试失败也只证明某项检查失败，不能单独证明选错路线。确定性判断需要**事先确认且可执行的目标或约束，以及与当前执行绑定的证据** |
| ② 定位回退点 | 人凭记忆判断"从哪一步开始错的" | 不能假装精确：错误可能远早于可见失败（错误接口假设直到集成时才暴露）；"测试最后一次通过"只是候选点。因果动作不可见时只能描述边界，不能编一个精确时间点 |
| ③ 生成新轨迹 | 人重写 prompt，带着教训重开 | **后见之明 ≠ 当时的知识**：事后发现的事实不能写进 prompt 假装当时就知道。还有同源偏差：同一个模型可能把旧错误重新表述，并在摘要时丢失反证 |
| ④ 安全接管 | 人决定回滚还是继续 | 自动回滚是有副作用的危险动作：旧 Agent 若仍在后台写入，新轨迹即使正确也会再次被破坏；验证与执行之间的状态可能已变化 |

难点①是最根本的。主观的"我觉得它跑偏了"无法自动化——必须先回答：**什么证据能确定性地证明"产物因为没达到既定要求而被返工"？**

## 四、自动化路径一：把提醒升级为门禁（hooks 三层拦截）

通用的自动化应覆盖执行前、执行后和交付前三个位置（以 Claude Code hooks 为例）：

```text
调用前（PreToolUse）：检查受保护路径和允许操作，越界则阻断
修改后（PostToolUse）：运行相关类型检查、lint 和局部回归
交付前（Stop）：      核对需求覆盖、变更范围和验收结果
失败后：              返回具体证据；达到重试上限则转人工
```

三个关键边界：

- **PreToolUse 能阻止操作，PostToolUse 执行时动作已经发生**，不能承担撤销职责；Stop hook 也有触发边界，不能独自充当最终验收。路径检查必须覆盖 Bash 等所有写入入口；强边界需要文件权限、隔离环境和受保护 CI 配合
- **验收标准必须独立于实现。**Cursor 推荐先写测试、确认失败、审查并提交，再要求 Agent 实现且不许改测试——若它能同时删断言、改脚本、改实现，"全绿"就失去意义。关键测试、检查配置和门禁脚本要被保护，并由独立 CI 重跑。测试之外仍需检查需求覆盖，因为既有测试未必表达了新需求
- **给自动修复设置上限**：轮次、时间和变更范围。超过上限时输出失败用例、最近一次变更和待决策事项，转人工。成效用越界修改次数、人工纠正次数、回退成本、验收后缺陷来衡量，而不能只看 Agent 是否宣称完成

多 Agent 评审适合补充语义检查：执行者完成后，评审者用新上下文只读任务契约、diff 和必要代码，逐条报告不符合项。

## 五、自动化路径二：omha 自动蝴蝶效应（纠偏闭环的实现样本）

hooks 门禁解决的是"越界拦截"，而第三节的难点①——**不靠人盯、确定性地发现因果漂移**——需要一个更完整的证据链设计。omha（本地跨 provider 的多 Agent 编排 CLI）的自动蝴蝶效应功能给出了一份工程答卷，分**手动诊断层**和**自动观察层**。

### 5.1 手动层：蝴蝶效应的决策契约

手动 skill（触发词"月光宝盒/蝴蝶效应"）定义了漂移判定的严格契约：

- 漂移要求**一个产物版本因为未达到预期结果或适用约束而被返工**。要求先于产物存在、验收后的正常演进、没有产物返工的反复解释——都是 no-op
- 回退到**最早那个"换掉它就能避免返工"的 Agent 动作**；因果动作不可见时描述边界，不伪造精度
- 保留原始目标和已验收的决策；**把事后发现的事实转换为"去检查、复现、验证"的指令**，而不是假装回退点就知道
- 证据不足时直接返回"无可靠漂移或回退点"，并指明缺什么证据

输出是**回退建议 + 一段可独立使用的修正 prompt**——契约里明确写着：这是 advice，绝不暗示回退已经发生。

### 5.2 自动层：证据链如何建立

```text
执行前：宿主提供验收命令
  → 冻结命令、参数、可执行文件和 harness 哈希，存入 run
       │
执行中：持有 worktree 租约，worker 运行前做有界的元数据快照（不留文件内容）
       │
执行后：worker 完成 + 改动了 worktree + 完整稳定的验收检查失败
  → 确立"产物版本 + 窄化宿主反馈：原验收要求未达成"
  （provider 的退出码或措辞不能充当这个反馈）
       │
后续授权尝试：从同一候选产物开始 + 产出不同内容
  → 检测器核对时序要求、反馈、版本哈希、可见任务动作
       │
命中：定位到最早的受支持任务尝试，生成确定性报告
  → at-most-once claim 后发出默认 file 交接（含续写 prompt，不启动模型）
```

四个设计细节值得单独拎出来：

**1. 验收先行，既是预防也是数据源。**验收命令在**执行前**冻结——这本身就是 Level 0 预防（先定义"什么算对"），同时为检测器提供不可篡改的判定基准。冻结包括 harness 文件的哈希：**验收脚本变了，前后两次失败就不可比，直接 no-op**。

**2. 检测器是确定性代码，模型只能在校验过的边界内提案。**核心检测是纯函数：核对事件时序、产物版本哈希、宿主反馈和返工动作，产出确定性结论。即使用 `--analyze` 调用模型做分析，模型的每个提案也会被**回验**——回退边界必须等于确定性检测已支持的边界，修正 prompt 必须包含全部应保留的约束，否则丢弃。这正是 Level 4"要证据不要断言"思想在架构里的体现：不信任模型的口头判断，只信任被证据约束的判断。

**3. 修正 prompt 把"后见之明"转成"验证指令"。**生成的续写 prompt 结构固定：原始目标 → 产物标识 → "继续之前，先检查产物和相关历史、复现报告的失败、逐条验证约束；**把后来的发现当作要执行的检查**" → 约束清单 → 已验收决策清单 → "声明完成前先验证产物"。难点③就这样被契约化处理了。

**4. 安全边界写在机制里，而不是靠自觉。**每次运行最多 0-3 次交接、1-1000 条观察（上限呼应"不恋战"原则）；交接是 at-most-once 的，崩溃后的未决 claim 可见为 uncertain，恢复时绝不静默重试；报告明确声明**不真的回退会话、不恢复文件**。

### 5.3 从建议到真实接续：cmux 原生 fork

默认交接只交付"建议 + prompt"。绑定原生 cmux 会话后，接续可以变成真实动作：在源会话的真实 checkpoint/turn 处 fork 历史 → 向新会话投递结构化续写消息 → **新会话显式 accept 之后才关闭源 surface**。接管未确认前源会话保持存活；不确定的 fork 绝不重复执行。建议与动作分离、动作以继任者确认为门槛——这是难点④"安全接管"的实现方式。

### 5.4 什么情况下它拒绝工作

边界声明和正路径同样重要。以下情况全部 no-op，不产生任何动作：

- 单个哈希变化（变化 ≠ 因果漂移）
- 验收通过后的正常演进、验收后的新工作
- 两次尝试之间有外部改动
- 验收 harness 不稳定或被改动、验收检查不完整、检查本身会修改产物
- provider 故障、写入中断、历史缺失或超出检测器上限

**一个诚实的"不工作"清单，恰恰是这个检测器可信的原因。**

## 六、对照分析：自动化覆盖了什么，没覆盖什么

把人工四级体系和自动化实现放在一起看：

| 人工环节 | 自动化对应机制 | 自动化程度 |
|---------|--------------|-----------|
| Level 0 预防 | hooks 前置拦截；执行前冻结验收、任务 DAG 所有权、worktree 租约 | ✅ 机制内建 |
| Level 1 发现跑偏 | 验收失败 + 版本哈希 + 时序的确定性检测 | ✅ 自动，无需人盯 |
| Level 2 定位回退点 | 因果动作定位 + 最早受支持尝试 | ✅ 自动，但输出是建议 |
| Level 3 重启新轨迹 | 修正 prompt 生成 + file 交接 / cmux fork | ⚠️ 半自动：prompt 自动，执行需授权 |
| Level 4 验收闭环 | 独立 CI 重跑；检测器本身就是验收驱动；模型提案回验 | ✅ 架构级内建 |
| 真实回退/恢复文件 | —— | ❌ 明确不做 |

没覆盖的部分同样说明问题：

- **语义层面的跑偏检测不到。**自动层只认"冻结的验收要求未达成"这一种反馈；验收检查写不出来（比如"这个交互手感不对"）的漂移，依然要靠人
- **多 Agent 并发的外部冲突不在文件隔离范围内。**worktree 隔离文件，不能隔离共享数据库、远端服务和合并语义
- **交互式会话仍需显式历史。**自动观察不延伸到任意终端会话，也没有后台守护进程
- **"重启"的执行权留在人手里。**系统生成建议和 prompt，甚至能 fork 会话，但写权限、接管确认、源会话退役都要显式授权。这是设计选择，不是能力缺失

## 七、核心洞察

**1. 纠偏自动化的本质，是把"注意力问题"转换成"证据问题"。**人工体系的瓶颈是"人得盯着"；工程解法是先把"什么算对"冻结成验收命令，再让"是否跑偏"变成对时序、哈希、反馈的确定性核对。能自动化的不是判断力，而是证据链。

**2. 检测器的可信度来自它的 no-op 清单。**宁愿漏报不误报——把"正常演进"误判为"漂移"的代价（错误回滚、丢失工作）远大于漏掉一次漂移的代价。任何自动纠偏系统都应先写清楚"什么情况下我拒绝工作"；没有可靠判据时输出"不确定"，不能把模型置信度包装成事实。

**3. 模型的位置：在证据划定的边界内提案，而不是发明边界。**确定性检测器负责"是否漂移、漂到哪"，LLM 最多负责"怎么把修正 prompt 写得更好"，且输出必须回验。这是对 Level 4"不接受口头修复"最彻底的贯彻——连纠偏系统自己的模型调用也不例外。

**4. 人工四级体系并没有被取代，而是被分层接管了。**写得出的验收 → 自动检测；写不出的验收 → 人工盯防 + 手动蝴蝶效应诊断；跨会话反复出现的同类错误 → 落盘到 CLAUDE.md 变成预防。三者是分工，不是替代。自动化程度应由证据质量与可恢复性决定，不能由"支持自动重试"推出"可以无人值守"。

**5. 控制跑偏的终极目标：让错误方向尽早产生可观察的失败信号，让恢复代价保持可控。**提示词负责说明目标，工程系统负责让偏离被发现、被阻止、被恢复。

## 总结

- Agent 跑偏的三大根源是假设叠加、开放解空间 × 隐式上下文不足、长对话漂移；纠偏本质是**打断错误自增强回路**。注意区分 context rot（能力衰减）与 context drift（目标偏离）
- 人工纠偏按成本分层：Level 1 秒级打断（带证据的纠正）、Level 2 分钟级回滚（会话/文件/外部状态三方核对）、Level 3 反复不成果断重开（先保存交接状态）、Level 4 证据闭环（不接受口头修复），外加 Level 0 预防前移（验收契约五项、约束持久化、长任务状态管理）
- 人工体系的缺口是每个环节都依赖人的注意力；自动化的四大难点是：因果证据、回退点精度、后见之明的转化、安全接管
- 两条自动化路径：**hooks 三层门禁**（越界拦截 + 独立验收 + 有限重试转人工）和 **omha 自动蝴蝶效应**（验收冻结 + 版本哈希 + 时序 + 宿主反馈建立因果漂移证据；确定性检测器划定边界、模型提案回验；后见之明转成验证指令；上限、at-most-once、继任者确认保障接管安全）
- 纠偏的终局不是"全自动"，而是**分层接管**：机制管证据，模型管表达，人管判断
