# Agent 跑偏应对方案分析：从人工纠偏四级体系到自动蝴蝶效应

> 用 AI Coding Agent 写代码，跑偏是常态而不是事故。本文综合一份覆盖 Anthropic 官方文档与中文社区实践的纠偏方法调研，以及 omha 项目中"自动蝴蝶效应"的真实工程实现，回答一个问题：**人工纠偏的哪些环节可以自动化，自动化的边界又在哪里？**

## 一、先归因：Agent 为什么跑偏

纠偏手段取决于跑偏原因。社区共识把根源归为三类：

| 根源 | 机制 |
|------|------|
| **假设叠加** | LLM 的统计偏置是"强行给解"而不是追问缺失信息。每个假设都是一次抛硬币，串起来就是"能跑但不对"的代码 |
| **解空间太开放 × 隐式上下文不足** | 解法越开放、依赖的隐式知识越多，选错路概率越高。且 Agent **不会在工作中学习**——每次新会话都是"新员工"，不知道团队约定 |
| **长对话漂移** | 上下文污染、目标漂移、摘要失真、指令层级混杂、**错误自增强**（错误假设滚雪球）、记忆策略不稳、工具结果原始注入，七大机制叠加 |

一句话：**纠偏的本质是打断"错误自增强"回路，把上下文重置到干净锚点。** 所有有效手段都是这句话的具体化。

## 二、人工纠偏体系：按成本分层的四级方案

调研（8 个来源，含 Anthropic 官方文档）给出一个按纠偏成本从低到高的完整方法体系。

### Level 1：跑偏进行中——秒级打断

- **Esc 中断**：发现方向不对立刻按 Esc，上下文保留，直接给新指令转向。Anthropic 官方原则是 **"Course-correct early and often"**——纠偏越快，结果越好、越快
- **中途插话**：Agent 工作时排队补充约束（如"别动 X 文件"）
- **重锚定提示词**：

```text
请暂停。当前目标是 X，约束是 Y 和 Z，已确认不做 W。复述你的理解再继续。
```

注意：实测表明这类话术**有时不生效**——失效本身就是该升级手段的信号。

### Level 2：刚跑偏完——分钟级回滚

- **`Esc + Esc` / `/rewind`**：Claude Code 检查点可分别恢复"仅对话 / 仅代码 / 两者"。局限：Bash 命令造成的文件改动、后台 subagent 的编辑**不在快照内**，检查点不能替代 git
- **"Undo that"**：让 Agent 自己撤销刚才的改动
- **git 兜底**：`git checkout .`，或开 task 前先 commit；多 Agent 并发用 git worktree 物理隔离
- **`/branch` 分叉**：保留当前会话，开分支试另一种方案

### Level 3：反复纠不正——重启（关键法则）

**"两次纠正法则"（Anthropic 官方）**：同一问题在同一会话纠正超过 2 次，上下文已被失败尝试污染——`/clear` 开新会话，把学到的东西写进更精确的初始 prompt。**干净会话 + 好 prompt 几乎总是胜过堆积纠正的长会话。**

上下文断裂的识别信号：Agent 突然换技术栈、忘记已定的方案、代码风格突变、重复问已答过的问题。

### Level 4：验收层——不接受"口头修复"

最容易被忽视的一层。**"看起来修好了"是纠偏最大的假阳性**：

- **证据五问**：①检查了哪些文件？②定位到什么？③打了什么 patch？④build 过了吗？⑤**什么检查能证明原问题真的消失了？** diff 合理 ≠ 修复，build 通过 ≠ 行为正确
- **测试门禁**：测试不过 = 任务没完，把失败输出回喂给 Agent 自修复。实测此举把"Agent 改坏东西"的比例降了约 80%
- **要证据不要断言**：测试输出、运行截图、命令返回值——审查证据比自己重跑验证快得多
- **Fresh-context 评审**：用新 subagent 只看 diff 和验收标准，不受产生代码的推理过程影响

### Level 0：预防——最便宜的纠偏是不跑偏

1. **先规划后写码**：plan mode 在写码前显式暴露假设
2. **收紧解空间**：prompt 更 directive；大任务拆小，人留在决策环里
3. **约束持久化**：CLAUDE.md 写清技术栈、约定、"绝不做的事"——约定不落盘等于不存在。但注意注意力预算，规则不是越多越好
4. **上下文卫生**：一个对话一个任务；任务间 `/clear`；长会话主动 `/compact`
5. **长任务架构级防偏**：任务状态与对话历史分离（维护结构化的"当前目标/已确认约束/已排除方案"）、周期性重锚定、"计划-执行-校验"三段式

### 速查表：症状 → 手段

| 症状 | 首选手段 | 升级路径 |
|------|---------|---------|
| 正在写错方向 | Esc 打断 + 一句纠正 | 重锚定提示词 |
| 改完发现不对 | "Undo that" / `/rewind` | git checkout |
| 想对比两种方案 | `/branch` 或 rewind 后换 prompt | worktree 并行 |
| 纠了 2 次还错 | **`/clear` 重开**（带新 prompt） | 拆小任务再试 |
| 说修好了但存疑 | 要证据（测试输出/截图） | fresh subagent 评审 |
| 同类错误跨会话反复出现 | 写入 CLAUDE.md / rules | 加 lint/test 门禁 |
| 长任务越跑越偏 | 周期性重锚定 | 改为 plan-execute-verify 流程 |

**核心心法**：纠偏要快（early and often）、要狠（2 次不成就重开，不恋战）、要闭环（没证据不算修完）、要前移（预防比纠正便宜一个数量级）。

## 三、人工体系的缺口：每个环节都假设"有人在盯着"

四级体系很完整，但它有一个隐含前提：**人始终在场，且注意力在线。**

把纠偏流程拆开看，每一步的成本都在人身上：

| 环节 | 人工做法 | 自动化难点 |
|------|---------|-----------|
| ① 发现跑偏 | 人盯着输出，觉得"不对劲" | **变了 ≠ 漂了**：文件哈希变化只是变化的证据，不是因果漂移的证明。正常演进、验收后的新工作、外部改动都会造成变化 |
| ② 定位回退点 | 人凭记忆判断"从哪一步开始错的" | 不能假装精确：因果动作不可见时，只能描述边界，不能编一个精确时间点 |
| ③ 生成新轨迹 | 人重写 prompt，带着教训重开 | **后见之明 ≠ 当时的知识**：事后发现的事实不能直接写进 prompt 假装当时就知道，否则新轨迹建立在"未来信息"上 |
| ④ 安全接管 | 人决定回滚还是继续 | 自动回滚是有副作用的危险动作：并发冲突、崩溃中断、重复触发都要防 |

难点①是最根本的。主观的"我觉得它跑偏了"无法自动化——你必须先回答：**什么证据能确定性地证明"产物因为没达到既定要求而被返工"？**

omha 项目的自动蝴蝶效应（automatic butterfly）实现，正是围绕这四个难点给出的一份工程答卷。

## 四、omha 自动蝴蝶效应：纠偏自动化的一个实现样本

omha 是一个本地跨 provider 的多 Agent 编排 CLI（Claude/Codex/Kimi 路由 + 任务 DAG + 交接管理）。它的蝴蝶效应功能分两层：**手动诊断层**（butterfly-effect skill）和**自动观察层**（automatic butterfly）。

### 4.1 手动层：蝴蝶效应的决策契约

手动 skill（触发词"月光宝盒/蝴蝶效应"）定义了漂移判定的严格契约：

- 漂移要求**一个产物版本因为未达到预期结果或适用约束而被返工**。要求先于产物存在、验收后的正常演进、没有产物返工的反复解释——都是 no-op
- 回退到**最早那个"换掉它就能避免返工"的 Agent 动作**；因果动作不可见时描述边界，不伪造精度
- 保留原始目标和已验收的决策；**把事后发现的事实转换为"去检查、复现、验证"的指令**，而不是假装回退点就知道
- 证据不足时直接返回 `No reliable drift or rewind point detected`，并指明缺什么证据

输出是**回退建议 + 一段可独立使用的修正 prompt**——契约里明确写着：这是 advice，绝不暗示回退已经发生。

### 4.2 自动层：证据链如何建立

自动层回答了最难的环节①——**怎么不靠人盯，确定性地发现因果漂移**。它的事件链设计：

```text
执行前：宿主提供验收命令
  → 冻结命令、参数、可执行文件和 harness 哈希，存入 run
       │
执行中：持有 worktree 租约，worker 运行前做有界的元数据快照（不留文件内容）
       │
执行后：worker 完成 + 改动了 worktree + 完整稳定的验收检查失败
  → 确立"产物版本 + 窄化宿主反馈：原验收要求未达成"
  （provider 的退出码或措辞不能充当这个反馈）
       │
后续授权尝试：从同一候选产物开始 + 产出不同内容
  → 检测器核对时序要求、反馈、版本哈希、可见任务动作
       │
命中：定位到最早的受支持任务尝试，生成确定性报告
  → at-most-once claim 后发出默认 file 交接（含续写 prompt，不启动模型）
```

四个设计细节值得单独拎出来：

**1. 验收先行，既是预防也是数据源。** 验收命令在**执行前**冻结——这本身就是 Level 0 预防（先定义"什么算对"），同时为检测器提供了不可篡改的判定基准。冻结包括 harness 文件的哈希：**验收脚本变了，前后两次失败就不可比，直接 no-op**。

**2. 检测器是确定性代码，模型只能在校验过的边界内提案。** `detectDrift` 是纯函数：核对事件时序、产物版本哈希、宿主反馈和返工动作，产出确定性结论。即使用 `--analyze` 调用模型做分析，模型的每个提案也会被**回验**——回退边界必须等于确定性检测已支持的边界，修正 prompt 必须包含全部应保留的约束，否则丢弃。这正是 Level 4"要证据不要断言"思想在架构里的体现：不信任模型的口头判断，只信任被证据约束的判断。

**3. 修正 prompt 把"后见之明"转成"验证指令"。** 生成的续写 prompt 结构固定：原始目标 → 产物标识 → "继续之前，先检查产物和相关历史、复现报告的失败、逐条验证约束；**把后来的发现当作要执行的检查**" → 约束清单 → 已验收决策清单 → "声明完成前先验证产物"。难点③就这样被契约化处理了。

**4. 安全边界写在机制里，而不是靠自觉。** 每次运行最多 0-3 次交接、1-1000 条观察（上限呼应"两次纠正法则"——不恋战）；交接是 at-most-once 的，崩溃后的未决 claim 可见为 uncertain，恢复时绝不静默重试；报告明确声明**不真的回退会话、不恢复文件**。

### 4.3 从建议到真实接续：cmux 原生 fork

默认交接只交付"建议 + prompt"。当绑定原生 cmux 会话后，接续可以变成真实动作：在源会话的真实 checkpoint/turn 处 fork 历史 → 向新会话投递结构化续写消息 → **新会话显式 accept 之后才关闭源 surface**。接管未确认前，源会话保持存活；不确定的 fork 绝不重复执行。

建议与动作分离、动作以继任者确认为门槛——这是环节④"安全接管"的实现方式。

### 4.4 什么情况下它拒绝工作

边界声明和正路径同样重要。以下情况全部 no-op，不产生任何动作：

- 单个哈希变化（变化 ≠ 因果漂移）
- 验收通过后的正常演进、验收后的新工作
- 两次尝试之间有外部改动
- 验收 harness 不稳定或被改动、验收检查不完整、检查本身会修改产物
- provider 故障、写入中断、历史缺失或超出检测器上限

**一个诚实的"不工作"清单，恰恰是这个检测器可信的原因。**

## 五、对照分析：自动化覆盖了什么，没覆盖什么

把人工四级体系和 omha 自动层放在一起看：

| 人工环节 | omha 对应机制 | 自动化程度 |
|---------|--------------|-----------|
| Level 0 预防 | 执行前冻结验收、任务 DAG 所有权、worktree 租约 | ✅ 机制内建 |
| Level 1 发现跑偏 | 验收失败 + 版本哈希 + 时序的确定性检测 | ✅ 自动，无需人盯 |
| Level 2 定位回退点 | 因果动作定位 + 最早受支持尝试 | ✅ 自动，但输出是建议 |
| Level 3 重启新轨迹 | 修正 prompt 生成 + file 交接 / cmux fork | ⚠️ 半自动：prompt 自动，执行需授权 |
| Level 4 验收闭环 | 检测器本身就是验收驱动；模型提案回验 | ✅ 架构级内建 |
| 真实回退/恢复文件 | —— | ❌ 明确不做 |

没覆盖的部分同样说明问题：

- **语义层面的跑偏检测不到。** 自动层只认"冻结的验收要求未达成"这一种反馈，任意的语义批评、reviewer 的主观意见都不在覆盖范围内。验收检查写不出来（比如"这个交互手感不对"）的漂移，依然要靠人。
- **交互式会话仍需显式历史。** 自动观察不延伸到任意终端会话，也没有后台守护进程——对话形式的漂移要手工喂历史 JSON 或在当前会话里手动诊断。
- **"重启"的执行权留在人手里。** 系统生成建议和 prompt，甚至能 fork 会话，但写权限、接管确认、源会话退役都要显式授权。这是设计选择，不是能力缺失。

## 六、核心洞察

**1. 纠偏自动化的本质，是把"注意力问题"转换成"证据问题"。** 人工体系的瓶颈是"人得盯着"；omha 的解法是先把"什么算对"冻结成验收命令，再让"是否跑偏"变成对时序、哈希、反馈的确定性核对。能自动化的不是判断力，而是证据链。

**2. 检测器的可信度来自它的 no-op 清单。** 宁愿漏报不误报——把"正常演进"误判为"漂移"的代价（错误回滚、丢失工作）远大于漏掉一次漂移的代价。任何自动纠偏系统都应先写清楚"什么情况下我拒绝工作"。

**3. 模型的位置：在证据划定的边界内提案，而不是发明边界。** 确定性检测器负责"是否漂移、漂到哪"，LLM 最多负责"怎么把修正 prompt 写得更好"，且输出必须回验。这是对 Level 4"不接受口头修复"最彻底的贯彻——连纠偏系统自己的模型调用也不例外。

**4. 人工四级体系并没有被取代，而是被分层接管了。** 写得出的验收 → 自动检测；写不出的验收 → 人工盯防 + 手动蝴蝶效应诊断；跨会话反复出现的同类错误 → 落盘到 CLAUDE.md 变成预防。三者是分工，不是替代。

## 总结

- Agent 跑偏的三大根源是假设叠加、开放解空间 × 隐式上下文不足、长对话漂移；纠偏本质是**打断错误自增强回路**
- 人工纠偏按成本分层：Level 1 秒级打断、Level 2 分钟级回滚、Level 3 两次不成果断重开、Level 4 证据闭环，外加 Level 0 预防前移
- 人工体系的缺口是每个环节都依赖人的注意力；自动化的四个难点是：因果证据、回退点精度、后见之明的转化、安全接管
- omha 自动蝴蝶效应的答卷：**验收冻结 + 版本哈希 + 时序 + 宿主反馈**建立因果漂移证据；确定性检测器划定边界、模型提案回验；后见之明转成验证指令；上限、at-most-once、继任者确认保障接管安全
- 纠偏的终局不是"全自动"，而是**分层接管**：机制管证据，模型管表达，人管判断
